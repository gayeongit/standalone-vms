**Team Clue | VEDA 3기 | 2026.02**

> v1 개발 중 확인된 기술 한계 + 원래 v2 예정이었던 항목을 정리한 문서

## 1. v1에서 발견된 기술 한계 → v2 해결 필요

### 1.1 영상 렌더링: appsink + QOpenGLWidget 전환

**v1 문제**: `d3d11videosink`가 런타임 윈도우 핸들 교체(`set_window_handle`)를 지원하지 않음

| v1 (현재) | v2 (개선) |
|-----------|-----------|
| `d3d11videosink` → QWidget `winId()` 직접 렌더링 | `appsink` → `QImage` → `QOpenGLWidget` 렌더링 |
| 화면 전환 시 해당 채널 파이프라인 재시작 (B 전략) | 화면 전환 시 위젯만 교체, **재연결 0** |
| 동일 채널 다중 셀 배치 시 마지막 셀만 렌더링 (d3d11 단일 핸들 제약) | `QImage` 기반이므로 동일 프레임을 여러 위젯에 paint 가능 |
| `BitBlt` 기반 스크린 캡처 (d3d11 오버레이 못 잡음 우회) | `appsink`에서 프레임 직접 추출 → 고화질 캡처 |
| 창 가려지면 캡처 실패 가능 | 파이프라인 내부 프레임이므로 항상 정확 |

**구현 방향**:
```
GStreamer 파이프라인:
  rtspsrc → depay → decode → videoconvert → appsink (caps: video/x-raw,format=RGB)

Qt 렌더링:
  appsink의 new-sample 시그널 → GstBuffer → QImage 변환
  → QOpenGLWidget::paintEvent()에서 렌더링
```

**재사용 가능한 v1 구조**: `ChannelSessionManager` 그대로 유지. `StreamPlayer` 내부만 교체.

### 1.2 클립/스냅샷 캡처 개선

| v1 (현재) | v2 (개선) |
|-----------|-----------|
| `BitBlt` 스크린 캡처 (Windows 네이티브) | `appsink` 프레임에서 직접 추출 |
| OSD가 스냅샷에 포함됨 | 순수 영상만 캡처 가능 (OSD 포함 옵션 선택) |
| 메모리 버퍼 300프레임 상한 | 디스크 직접 쓰기 (FFmpeg 파이프) |

### 1.3 인코딩 비동기 처리

| v1 (현재) | v2 (개선) |
|-----------|-----------|
| `stopAndEncode()` 동기 실행 (UI 블로킹) | `QtConcurrent::run()` 또는 `QThread` 비동기 인코딩 |
| PNG 저장 루프에 `processEvents()` 추가로 체감 개선 | 완전 비동기 + 완료 시그널로 UI 응답성 보장 |
| 로그아웃/UGV 출동 시 저장 완료 대기가 동기적 | 시그널 체인으로 비동기 완료 후 화면 전환 |

> v1 대응: PNG 저장 루프에 `processEvents()` 추가 (앱 멈춤 체감 개선)  
> v1 제한: 클립 저장(`stopAndEncode`)과 Playback 내보내기(`openExportDialog`) 모두 동기 ffmpeg 실행. 대용량 시 UI 스터터 발생 가능  
> v2 예상 작업량: `stopAndEncode()` + `openExportDialog()` 2개 함수 + 호출부 시그널 변경 (**소규모**)

### 1.4 OSD 영상 오버레이

**v1 문제**: `d3d11videosink`가 HWND 전체를 D3D11 swap chain으로 렌더링하여 같은 HWND 자식인 Qt OSD 라벨을 매 프레임 덮어씀

| v1 (현재) | v2 (개선) |
|-----------|-----------|
| `d3d11videosink`가 host HWND 전체를 점유 → Qt 자식 위젯 렌더링 덮어씀 | `appsink` + `QOpenGLWidget`이면 Qt 위젯 레이어링 정상 동작 |
| `WA_NativeWindow` 없으면 OSD 안 보임, 있으면 배경 박스/테두리 발생 (순환 모순) | 같은 렌더 파이프에서 영상+OSD 합성 → 완전 투명 오버레이 가능 |
| 클립 버튼에 타이머 표시 (`⏹ 00:01:23`) 로 우회 | 영상 위 `⏺ CLIP 00:01:23` OSD 복원 |
| 타이머 `raise()` 반복 호출로 OSD 유지 시도 → 플랫폼 의존적/불안정 | `raise()` 워크어라운드 불필요 |

> v1 대응: OSD에 `WA_NativeWindow` + `WA_TranslucentBackground` + 주기적 `raise()` 적용. OSD는 유지되나 완전 투명은 불가 (반투명/배경 잔상 일부 허용)
> v1 트러블슈팅 기록: `docs/troubleshooting/troubleshooting_osd_overlay.md`
> v2 예상 작업량: appsink 전환 시 **자동 해결** (추가 작업 0)

## 2. 통신 아키텍처: WebSocket/MQTT (미정)

**v1**: UGV는 MQTT 더미, 서버-VMS 간 통신 프로토콜 미정의
**v2**: 서버 ↔ VMS 간 통신 프로토콜 **WebSocket 또는 MQTT (미정, v2 착수 전 확정 필요)**

> [!IMPORTANT]
> VMS ↔ 서버 간 프로토콜(WebSocket vs MQTT)은 v2 개발 착수 전에 확정해야 함. 서버 팀과 협의 후 결정.

### 2.1 통신 구조

```
┌──────────────┐  WebSocket / MQTT  ┌──────────────┐
│              │◄──────────────────►│              │
│   VMS (Qt)   │      (미정)        │   서버       │
│              │                    │              │
└──────────────┘                    └──────────────┘
```

> 서버 ↔ UGV(중계기) 간 통신은 서버 측 영역이므로 본 문서 범위 밖.

### 2.2 메시지 범위 (VMS가 주고받는 것만)

| 채널 | 방향 | 내용 |
|------|------|------|
| UGV 제어 | VMS → 서버 | 드라이브 명령, PTZ 명령 |
| UGV 상태 | 서버 → VMS | RSSI, 배터리, GPS 좌표 |
| 이벤트 알림 | 서버 → VMS | 모션 감지, 침입 감지 등 실시간 이벤트 |
| 장치 상태 | 서버 → VMS | 채널 연결/끊김 상태 |
| 백업 상태 | 서버 → VMS | Archive 용량·보관일수 정보 |

### 2.3 Qt 구현 방향

- WebSocket: `QWebSocket` (Qt WebSockets 모듈) / MQTT: `QMqttClient` (Qt MQTT 모듈)
- 싱글턴 통신 클래스 — 자동 재연결, 메시지 라우팅
- JSON 기반 메시지 포맷

## 3. 원래 v2 예정이었던 항목

### 3.1 ONVIF Discovery

| 항목 | 설명 |
|------|------|
| 방식 | gSOAP 또는 `QUdpSocket` WS-Discovery |
| 목적 | CCTV 자동 검색 + RTSP URL 자동 획득 |
| 현재 | v1은 하드코딩 장치 목록 + 수동 RTSP URL |

### 3.2 DB 연동

| 항목 | 설명 |
|------|------|
| 대상 | 장치 목록, 이벤트 로그, 사용자 설정 |

| 현재 | v1은 `QSettings` + 메모리 변수 + 하드코딩 |

## 4. 우선순위 정리

| 순위 | 항목 | 이유 |
|------|------|------|
| **P0** | VMS-서버 프로토콜 확정(WebSocket/MQTT) | UGV 실연동 필수. 이벤트 실시간 수신 필수 |

## 8. v2 사전 결정 항목 (개발 착수 전 확정 필요)

기준일: 2026-02-27

### 8.1 설정 저장 방식
- 아래 중 하나를 확정:
  - `QSettings` 유지
  - 로컬 JSON 전환
  - 하이브리드(로컬 캐시 + 서버 원본)
- 단일 클라이언트/오프라인 우선이면 가독성/백업 이식성 측면에서 JSON 우선 검토

### 8.2 서버 설정 백업/동기화 여부
- 사용자 설정을 서버에 백업/동기화할지 결정
- 다중 클라이언트/세션 이식성이 필요할 때 권장

### 8.3 통신 프로토콜 최종 확정
- VMS <-> 서버 프로토콜: `WebSocket` vs `MQTT` 최종 확정
- 해당 결정이 명령/텔레메트리 클라이언트 구현 세부를 결정함

### 8.4 런타임 반영 vs 재시작 반영 매트릭스
- 설정별 즉시 반영 / 재시작 필요 여부 정의
- v1은 현재 구현 항목 전부 즉시 반영 정책

### 8.5 FFmpeg 의존성 배포 정책
- FFmpeg를 외부 의존(PATH 기반)으로 둘지, 배포 패키지에 번들/내장할지 결정
- 시작 진단 및 기능별 대체 동작 정의 필요

### 8.6 아카이브 정책 소유 경계
